# omop-duck-db and the OHDSI tools

omop-duck-db exists to run OMOP studies on DuckDB databases. OHDSI already has tools for most of what a study needs, so the
rule for this package is:

1. **Study logic goes in standard OHDSI artifacts** (Circe/ATLAS cohort definitions, concept sets, OHDSI SQL, HADES
   settings objects), so it is portable to ATLAS and to sites that do not run this package.
2. **The package supplies what the OHDSI tools do not**: PCORnet-to-OMOP ETL, DuckDB/Arrow/lakehouse plumbing, vocabulary loading,
   a Java-free Circe compiler, bridges that make a DuckDB CDM usable by HADES, and checks that the data are fit for the study.
3. **Where the package re-implements an OHDSI tool, it says so, covers only a subset, and is checked against the tool.**

This page audits the package against that rule, and records what was checked against the real tools. The checks ran with
CohortGenerator, CirceR, FeatureExtraction, Achilles 1.7.2, DataQualityDashboard, PhenotypeLibrary, CohortDiagnostics and
PatientLevelPrediction (DatabaseConnector 8.0.0, duckdb 2.0.0).

**Studies use the validated OHDSI tools; the package adds features to them, not replacements.** A feature that OMOP has no
definition for (RUCA, SDI, a site score) is written to the CDM with `write_custom_covariates()` and read with FeatureExtraction
like any other covariate; an alternative definition of an existing feature gets its own concept id and is compared with the
standard one (`compare_feature_tables()`) before a study picks one.

## What to change next

1. **Cohorts**: add every new inclusion/exclusion rule as Circe JSON first (done for the metformin-only exclusion and the diabetes
   phenotype, and now the index-stay cohort). `inst/cohorts/target_cohort.circe.json` is the index-stay cohort as Circe JSON and agrees with
   CirceR + CohortGenerator; it cannot express discharge disposition or a death-in-window follow-up (documented), so its SQL stays authoritative.
   Run a new definition through CirceR + CohortGenerator as well as the native compiler before relying on the native one.
2. **Run the official tools in CI** where HADES is installed (the R tests above skip cleanly otherwise).
3. **Charlson**: not a package decision. Downstream writes its own definition with `write_custom_features()` and compares it with FeatureExtraction's on real mapped data.
4. **DQD**: the per-concept checks of the official list (`plausibleGender`, `plausibleUnitConceptIds`, ...) are still not run; say so in every report.
5. **Keep the claim honest**: every function that overlaps an OHDSI tool says in its help page what it covers and what it does not.

## Checked against the official tools

| Tool | What was compared | Result |
|---|---|---|
| CirceR + CohortGenerator | The four `inst/cohorts/*.circe.json` files, rendered by CirceR and run on DuckDB, against the native compiler and `find_metformin_only_prediabetes_pcos()` | Same people in every cohort (`tests/testthat/test-circe-definitions.R`). The check found that the first version of `diabetes_phenotype.circe.json` was **not valid Circe** (age was written as a `DemographicCriteria` criterion instead of `DemographicCriteriaList`); fixed, and the native compiler now reads `DemographicCriteriaList`. |
| FeatureExtraction, visit counts | `extract_prior_utilization` against `useVisitConceptCountLongTerm` (365 days before, admission day excluded) | Identical counts (`test-ohdsi-parity.R`). |
| FeatureExtraction, measurement values | RUCA and SDI written by `write_geography_measurements()` read back as covariates | Works once `unit_concept_id` is 0: FeatureExtraction joins on the unit and silently skips rows where it is NULL (`test-geography.R`). |
| FeatureExtraction, Charlson | `extract_charlson_index` against `useCharlsonIndex` ("Romano adaptation") on the repo's comorbidity fixture, ICD codes mapped to standard concepts through the vocabulary | **Not equivalent.** 135 of 180 persons get the same index. Many of the 45 differences are the fixture's own probes (code normalization such as lower case and spaces, which FeatureExtraction cannot see, window-edge cases, Elixhauser probes) and 33 of 103 codes had no standard mapping, so this is not a clean estimate; but the two use different category definitions and different data (source codes vs standard concepts), so **do not mix them in one model or table**. A clean comparison needs real mapped data. |
| Achilles 1.7.2 | 14 analyses (0-5, 101, 103, 105, 108, 111-113, 200-202) on a small fixture | Counts identical. Two real differences, now fixed: the package used the population standard deviation and interpolated percentiles; Achilles uses the sample standard deviation (NULL for one value) and the discrete percentile (`tests/test_achilles.py` holds the official values). Cosmetic: analysis 0 stores the Achilles version in `stratum_2`; analysis 108 writes `12.0` on DuckDB. Achilles itself needs a workaround on this stack: with duckdb 2.0.0 and DatabaseConnector 8.0.0 `achilles()` fails with "Column ANALYSIS_ID does not exist in target table" (upper-case column names in `insertTable`). |
| DataQualityDashboard | Table and field checks on a planted-defect fixture | Agrees on person foreign keys, start-before-end and after-birth. Differences, now fixed: primary-key violations counted only the surplus copies (DQD counts every row of a duplicated key); after-birth ignored end dates and datetime fields. Still different: the package has no concept foreign-key, domain or class checks. `plausibleFutureDate` and `visitPersonMatch` are **not DQD checks**; they are labelled `check_origin = "omop-duck-db"` in the output. |
| PhenotypeLibrary + CirceR + CohortGenerator | All 707 library definitions classified by the native compiler; 80 sampled definitions run on a synthetic CDM (2,000 people, 30,000 events per domain, concepts and descendants from Athena) through both engines | The native compiler accepts 346 definitions and refuses the rest. Of 80 accepted ones, **80 return the same people and 79 the same start dates** (the other uses `CustomEra`). The first runs found real defects, all fixed: inclusion rules applied before the primary limit (231 vs 361 people), `Observation` entry events falling back to every visit (0 vs 1,887 people), ignored `AdditionalCriteria` and unevaluated criterion attributes, an unknown operator read as `=`, no era collapse or end strategy. `QualifiedLimit` is not applied by CirceR (only `ExpressionLimit`); the compiler follows CirceR. Repeat with `scripts/ohdsi_parity_phenotypelibrary.R`. |
| CohortDiagnostics | `executeDiagnostics()` on the diabetes phenotype and an inpatient-visit outcome cohort | Cohort entries and subjects identical to CohortGenerator and to `execute_circe_cohort()` (`scripts/ohdsi_parity_plp_cohortdiagnostics.R`). |
| PatientLevelPrediction | `getPlpData()` through `plp_database_details()` with demographics and a custom covariate; `createStudyPopulation()` (risk window 1-365 days); `runPlp()` with LASSO | The custom covariate is extracted; the study population and its outcome count equal a direct SQL count; `runPlp` finishes on the DuckDB-backed data (AUC 0.5 on random data, as it should be). |
| Index-stay cohort (`target_cohort.circe.json`) | CirceR + CohortGenerator, the native compilers (Python and R) and `target_cohort.sql` on one small CDM with the awkward cases (`scripts/ohdsi_parity_target_cohort.R`) | The official engine and both native compilers return the same people and index dates. The SQL differs in two cases Circe cannot express: discharge disposition without a death record, and a death inside the follow-up window when the observation period ends at death. Circe applies `PrimaryCriteriaLimit` before the inclusion rules, so the stay-level rules are correlated criteria of the entry event. |
